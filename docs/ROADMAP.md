# 路线图

优先级：先让电脑键盘链路稳定，再研究遥控器硬件限制。不以新增功能替代故障闭环。

## 1. 获得一次可解释的失败

新增有界、默认不落盘的状态时间线：Fn down/up、遥控器状态变化、generation、preparing、采集／播放计数和停止原因。只在用户主动导出时写脱敏诊断，不保存按键内容或音频。先证明失效发生在哪一层，再写最小复现与回归检查。

完成标准：发生“Fn 无字”时，能分辨没收到 Fn、被 remote 阻挡、音频未起、音频输出停或豆包会话结束，重置前能保留必要证据。

## 2. 修复状态一致性

依据上一步证据修复共同根因，重点检查延迟启动、取消、日志事件和实际音频状态的交叉；同步菜单状态与真实采集，解决豆包结束后仍转发的问题。自动恢复方案需先明确何时允许恢复，避免意外采集。

建议验收门槛（尚未完成）：至少 30 轮遥控器→键盘→遥控器交替，包含 STOP 后 0–400ms 内按下、短按、长按、取消；再按正常工作方式使用一个工作日。测试失败要定位原因，不能只反复重启。

## 3. 把原型做成可长期使用的工具

在稳定后评估以设备 UID／显式选择替代本机名称、以可靠事件或上游接口替代日志耦合；覆盖权限撤销、设备重连、日志轮换、睡眠恢复。测连续收音 CPU／RSS 和长时间启停。签名、公证、稳定安装路径与发布许可在实际分发前处理；不要提前加自动更新或开机启动。

## 4. 遥控器长按与一分钟限制：独立实验

| 方向 | 判断 | 验证条件 |
|---|---|---|
| 在 SayAll 上游改 RC003 协议／持续会话 | 保留遥控器麦克风体验，但不确定性高 | 同型号实机证明松键后仍有真实音频且超 60 秒连续；识别窗口持续不算通过 |
| 遥控器只作按钮，标准 USB／无线麦克风收音，继续豆包识别 | 推荐的替代方向，绕开 RC003 音频限制；需要另选设备 | 先用已有电脑麦克风验证交互，再由用户决定是否换硬件 |
| 替换桥接软件或遥控器 | 值得验证，不能假设“星多”代表适配 | 同机验证系统、型号、Fn 点按、连续音频、双端切换与许可 |

云端识别可以作为将来的识别路线选择，但当前保留豆包，无需先引入 API 成本。用户已拒绝本地转写。硬件采购、换服务、对外发布均不在本次整理范围内。
